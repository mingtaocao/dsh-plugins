分布式锁的三次迭代

分布式锁的难点不在“加锁”，而在“租约到期之后，谁也说不清锁还在不在”。这篇笔记按时间线记录三次关键迭代。

第一代：SET NX 加过期时间

用 SET key value NX PX 30000 一条命令完成占用与租约，解决了“加锁成功但设置过期失败”的原子性问题。但它没有解决业务执行时间超过租约的问题：锁自动释放后，两个持有者会同时认为自己持有锁。

第二代：看门狗续期

看门狗在租约过半时自动续期，并要求释放锁时校验持有者标识。续期把“执行时间不可预测”与“租约固定”解耦，代价是进程崩溃后最多等一个租约周期。

第三代：Redlock 的争议

Redlock 在多个独立 Redis 实例上多数派加锁，试图摆脱单点与时钟漂移。反对意见认为它依赖各节点时钟近似同步，在严重停顿时仍可能被两个客户端同时持有。工程结论通常是：宁可接受悲观锁的延迟，也不要依赖跨节点的时钟假设。
