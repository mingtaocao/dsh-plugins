缓存一致性：从 MESI 到 Caffeine

从 CPU 的多核一致性协议讲到进程内缓存框架，理解“缓存失效”为什么比“缓存命中”更难。

缓存并发Java

一、硬件层：MESI 解决的是可见性

多核 CPU 每个核心都有自己的私有缓存。MESI 用四种状态描述缓存行的归属：Modified、Exclusive、Shared、Invalid。写操作必须先取得独占，其他核心的副本被置为 Invalid，于是“读到最新值”成为协议保证。

代价是失效广播与总线流量：核心越多，写共享数据越贵。这也是@Contended、伪共享对齐存在的原因。

二、进程内：Caffeine 的 W-TinyLFU

Caffeine 用 Window TinyLFU 把新对象先放进一个小窗口，再由频率草图决定谁留在主区域。它解决的是“突发热点把长期热点挤掉”的问题，而不是一致性问题。

Window新写入的条目先进窗口，避免冷启动抖动。
TinyLFU4-bit 频率草图，用极小的内存估计访问频率。
Segmented LRU主区域用分段 LRU 保护高价值条目。

三、分布式：失效比更新便宜

跨进程缓存有两条路：写时更新（write-through）与写时失效（invalidate）。更新会带来“并发写覆盖”的顺序问题；失效只要求对方丢掉副本，下一次读取自然回源，因此更容易做对。

四、结论

缓存一致性的本质是：让谁在什么时候看不到旧值，变成一条可以验证的规则，而不是一次碰运气的写入。

工程上优先选择失效、给失效事件带上版本号、为回源路径准备降级与超时，比追求“强一致缓存”更现实。
