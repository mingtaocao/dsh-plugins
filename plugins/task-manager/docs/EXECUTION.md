# DSH 任务管理插件 — 分析、开发与测试执行规范

> 文档编号：DSH-TASK-EXEC · 版本：V1.0 · 日期：2026-11-14
> **AI Agent 的执行入口**。配套需求：《02-DSH任务管理插件-完整需求.md》。
> 目标：让 DSH 中的开发 Agent **按顺序分析 → 实现 → 实测 → 留证 → QA 复核**，不是只写代码或口头宣称成功。

## 0. 不可违反的执行原则

1. **先分析 DSH 当前代码与运行时，再选择插件 API**。文档中的 Host/Client/Repository 是逻辑职责，不代表已经验证当前项目目录或可调用 API。
2. 只以 DSH 官方支持的插件机制挂载；优先不改 DSH Core、不 monkey patch、不复制 DSH 内部 UI 私有实现。
3. **先读完整需求**：明确 V1 不包含今日任务、Backlog、计时、周期任务、云同步或 Agent 自动执行任务。
4. 以《完整需求》中的 `REQ-*` 作为功能判定依据，以本文 `DEV-*` 指导实施、`V-*` 指导验收。
5. 每个 P0 DEV 完成必须至少运行其关联 V 用例；**开发已提交 ≠ 验证通过**。
6. 验证只有 `PASS / FAIL / BLOCKED / NOT_RUN` 四种状态；`BLOCKED` 和 `NOT_RUN` 不能计为 PASS。
7. 无法获得运行环境、缺少工具或公开 SP 样本时记录阻塞，不能编造截图、命令输出、测试通过率、字段兼容性。
8. 所有真实用户数据和插件数据库必须备份、隔离；测试只使用独立的测试 Profile/数据库，绝不在用户真实数据上清库或做破坏性导入。
9. 每轮修改后只重测受影响用例和基础回归；发布前必须全量 P0 回归。
10. 遇到不明 DSH API，优先检查运行时能力、官方源码/类型声明、同版本内置插件、官方 Skill，再调整方案；不要自己发明 `ctx` 方法。
11. Agent 不得在“验证失败”后跳过；必须修复重测，或者列出阻塞原因、影响范围及证据。
12. 每个阶段结束更新本文状态，并留下最小可复现证据及 commit/hash（若适用）。

## 2. 架构规范（先按职责划分，再适配 DSH）

```text
DSH Web Profile
└── Task Management Plugin
    ├── Client：导航 / 项目侧栏 / 列表 / 看板 / 四象限 / 详情 / 导入向导
    │              │  DSH 官方通信/事件机制
    └── Host：TaskService / ProjectService / ImportService
                 ├── 统一 Repository + 原子事务
                 ├── 插件专有本地持久化 + schemaVersion/migrations
                 └── DSH JSON / Super Productivity JSON adapters
```

实现规则：
- 数据真相仅在 Host Repository；Client 统一调用类型化 Service。不得让某个视图单独存另一套任务。
- 项目、主任务、子任务共享内部 ID 命名空间，主键稳定；`projectId` 和 `parentId` 引用必须有约束。
- 采用**两级任务**模型；父子迁移、项目删除、批量导入必须事务化。
- `important=false, urgent=false` 在数据库、服务、UI、导入四层都一致；不能使用 `null` 表示未分类。
- 看板修改 `status`，四象限修改 `(important, urgent)`；相互独立。
- 子任务状态独立；看板/四象限只显示顶层主任务，子任务在主卡片内展示进度。
- 多视图排序相互独立（如 `listOrder/boardOrder/matrixOrder`）。
- 用 DSH 官方主题、Modal、Slot、插件生命周期；卸载释放服务/事件/UI 注册。
- 未确认的存储文件位置、API 名、CLI 名不得写成已实现事实。

### 2.1 推荐模块目录（仅供对齐职责，A 阶段确认后可修改）

### 3.1 DEV 完成的定义（DoD）

DEV 只有同时满足以下 6 条才能勾选：
1. 需求点对应代码已存在且类型检查/编译通过；
2. 有单测覆盖主要业务边界；
3. 关联 V 用例在真实运行环境被执行，状态 PASS；
4. 数据库或持久化中实际值被断言，不只靠 UI 截图；
5. 无新增 P0 回归、无私密数据泄露；
6. 验证证据、测试命令、运行环境、修改文件、失败修复记录已登记。

## 4. 确定性测试数据与环境隔离

每个 V 用例须使用全新、可重置的**独立测试数据**，严禁依赖上一用例的修改。内部 ID 可由系统生成，但测试记录必须有稳定 `externalKey` 或通过创建结果保存 ID 映射。

| 稳定键 | 项目 | 类型 | 标题 | 状态 | important | urgent | 预期 |
|---|---|---|---|---|---|---|---|
| P_DSH | — | 项目 | DSH 测试 | — | — | — | 活动项目 |
| P_LOCALPM | — | 项目 | LocalPM 测试 | — | — | — | 活动项目 |
| T_A | P_DSH | 主任务 | 开发任务管理 | todo | false | false | 看板待办/Q4，子任务 1/2 |
| S_A1 | T_A | 子任务 | 实现看板 | done | — | — | 独立完成 |
| S_A2 | T_A | 子任务 | 实现矩阵 | todo | — | — | 未完成 |
| T_B | P_DSH | 主任务 | 优化阅读器 | doing | true | false | 看板进行中/Q2 |
| T_C | P_LOCALPM | 主任务 | 修复代理问题 | blocked | false | true | 看板阻塞/Q3 |
| T_D | P_LOCALPM | 主任务 | 整理说明 | done | true | true | 看板完成/Q1；矩阵默认不显示 |

**固定断言**（seed 后，活动的所有项目 Scope）：
- 主任务 4 条，子任务 2 条；看板四列各 1 张主任务卡片。
- 矩阵默认隐藏完成：Q1=0、Q2=1、Q3=1、Q4=1；勾选「显示已完成」后 Q1=1。
- `T_A` 子任务进度 `1/2`；其父任务状态仍为 `todo`。
- 不可将 `S_A1/S_A2` 额外计入看板列或象限卡片数。

另准备以下**测试文件**（在开发时生成，不作为本文额外人工维护文档）：
- `fixtures/dsh-valid.json`：DSH 原生完整可导入状态，含项目、任务、子任务、归档状态和排序。
- `fixtures/dsh-duplicate.json`：相同来源 ID，用于重复导入的幂等检查。
- `fixtures/invalid-json.txt`：非法 JSON；`fixtures/orphan-task.json`：缺失父任务；`fixtures/duplicate-ids.json`：重复实体 ID；`fixtures/unsupported-version.json`：未知版本。
- `fixtures/sp-verified-<version>.json`：**必须来源于真实公开样本或依据官方测试 fixture 验证过的结构**，附 URL/commit/hash；没有则不得声称 `V-022 PASS`。
- `fixtures/performance.json`：20 项目、2,000 主任务、5,000 子任务的固定规模数据。

测试环境约束：导入文件均在本机读取，默认不向外发请求；每条测试结束恢复 fixture。不得拿用户的工作 Profile 做数据重置或破坏性实验。

## 5. 可执行验证 TODO（VERIFY）

**执行办法**：每条用例执行前将测试数据库恢复到该用例指定初始状态；按照步骤操作；用 UI 结果 + 持久化断言双重验证；按「用例模板」记载证据。指定「手动」时可人工执行，但需截图和实际 DB 结果。若没有自动化 UI 操作工具，必须 `BLOCKED` 相关用例，不能视为通过。

### 5.1 插件、项目和任务

- [ ] **V-001 插件安装/卸载（REQ-001/002，DEV-000）**
  前置：空测试 Profile。步骤：①按 A-002 已验证方式安装插件；②打开任务管理页面；③禁用并重新启用；④重启 DSH。断言：菜单/页面可见，无致命错误；禁用时 DSH 其他页面正常；再启用可访问。证据：安装日志、入口截图、重启日志。

- [ ] **V-002 首次创建项目（REQ-010，DEV-011）**
  前置：空任务库。步骤：①打开任务管理；②点击创建项目，输入“DSH 测试”；③保存；④刷新。断言：项目总数=1，名称正确、ID 非空；无隐式 Backlog/Inbox 项目。证据：创建前后数据查询、UI 截图。

- [ ] **V-003 项目改名/重名/排序（REQ-010，DEV-011）**
  前置：P_DSH、P_LOCALPM。步骤：①P_DSH 改名为“DSH 重构”；②尝试把 P_LOCALPM 改成同名；③调整项目排列；④刷新。断言：改名不更换项目 ID，任务仍关联；同名校验拒绝；排序持久化。证据：数据库断言、错误提示截图。

- [ ] **V-004 项目归档与恢复（REQ-010，DEV-011）**
  前置：标准 seed。步骤：①归档 P_DSH；②切换所有项目并查看列表/看板/矩阵；③从已归档入口恢复。断言：活动视图仅见 P_LOCALPM 两个主任务；归档不删除任务；恢复后原任务、子任务及顺序完整。证据：归档标记、数量断言。

- [ ] **V-005 项目删除保护（REQ-011，DEV-011）**
  前置：标准 seed。步骤：①删除 P_DSH，检查警示含主任务2、子任务2；②点取消；③再次删除并确认。断言：取消后数据完全不变；确认后仅 P_DSH 及其任务原子删除；P_LOCALPM 不变；若故意注入失败则全回滚。证据：确认弹窗、前后查询。

- [ ] **V-006 新任务默认值（REQ-020/021，DEV-020）**
  前置：只有空项目 P_DSH。步骤：①仅输入标题“新增待办”并保存；②查看列表、看板、矩阵；③查询持久化数据。断言：只有 1 条主任务，`status=todo,important=false,urgent=false,priority=normal,parentId=null`；看板待办 1，矩阵 Q4 1，**无未分类区**。证据：字段断言、三视图截图。

- [ ] **V-007 详情编辑/校验/安全（REQ-020/023，DEV-020）**
  前置：T_A。步骤：①打开详情，编辑描述、备注、优先级、截止日期；②保存重开；③尝试空标题/非法日期；④输入包含 `<script>` 的纯文本。断言：合法字段保留；无效输入拒绝且原值不变；脚本不会执行或污染 DSH UI。证据：查询、截图、无脚本执行证明。

- [ ] **V-008 四状态转换（REQ-022，DEV-020）**
  前置：T_A。步骤：①依次设置 doing→blocked→done→todo；②每次读取任务数据和看板列。断言：每步在且仅在对应状态列；done 时 completedAt 非空，恢复 todo 后清空；项目/象限不变。证据：状态记录、测试输出。

- [ ] **V-009 视图内排序独立（REQ-024，DEV-022）**
  前置：P_DSH 下创建同列/同象限 3 个主任务。步骤：①在列表调整顺序并记录；②在看板列内调整顺序；③在矩阵象限内调整顺序；④重启。断言：各视图顺序分别持久化；调整一个不改变另外两个已保存顺序。证据：三个 order 字段和截图。

### 5.2 子任务、看板和矩阵

- [ ] **V-010 子任务创建与层级限制（REQ-030，DEV-021）**
  前置：T_A，无子任务。步骤：①添加 S_A1、S_A2；②尝试为 S_A1 再建孩子；③检查父子及项目 ID。断言：主任务有 2 个子任务，均有 `parentId=T_A`、`projectId=P_DSH`；三级添加明确拒绝，无孤儿。证据：关系查询、错误反馈截图。

- [ ] **V-011 子任务独立完成（REQ-031，DEV-021）**
  前置：T_A 带 2 个未完成子任务。步骤：①勾选第一个；②核对所有视图显示 `1/2`；③把父任务标为 done；④再取消父任务完成。断言：父状态改变不覆盖子状态；子状态改变不自动完成父；`1/2` 保留。证据：父子状态断言、三视图截图。

- [ ] **V-012 主任务跨项目移动（REQ-032，DEV-021）**
  前置：标准 seed。步骤：①T_A 从 P_DSH 移到 P_LOCALPM；②分别查看两项目及所有项目的三种视图；③刷新。断言：父及两个子任务 `projectId=P_LOCALPM`，原项目不见，目标项目只出现 1 张父卡片，进度 `1/2`；引用不断裂。证据：事务查询、界面截图。

- [ ] **V-013 看板初始分组（REQ-042，DEV-031）**
  前置：标准 seed。步骤：①选择所有项目→看板；②核对四列；③展开 T_A。断言：todo/doing/blocked/done 各 1 张顶层卡片；列计数准确；T_A `1/2`，子任务不重复显示为顶层卡片。证据：卡片/列数量断言、截图。

- [ ] **V-014 四象限初始分组（REQ-043，DEV-032）**
  前置：标准 seed。步骤：①所有项目→矩阵，保持默认「不显示已完成」；②检查 Q1/Q2/Q3/Q4。断言：Q1=0、Q2=1(T_B)、Q3=1(T_C)、Q4=1(T_A)；没有第五象限；重要、紧急字段与象限一一对应。证据：字段断言、截图。

- [ ] **V-015 看板→列表/矩阵一致性（REQ-040/044，DEV-031/033）**
  前置：标准 seed。步骤：①看板把 T_A 从 todo 拖到 doing；②打开列表；③打开矩阵；④重启。断言：T_A `status=doing`；看板待办0、进行中2；列表显示进行中；矩阵仍 Q4；重启保持。证据：状态、数量、象限断言。

- [ ] **V-016 矩阵→看板/列表一致性（REQ-040/043，DEV-032/033）**
  前置：标准 seed。步骤：①矩阵把 T_A Q4 拖到 Q1；②打开看板和列表；③刷新。断言：`important=true,urgent=true`；Q4 少1、Q1 多1；`status=todo` 不变，看板仍待办；刷新保持。证据：字段、数量和截图。

- [ ] **V-017 当前/所有项目 Scope（REQ-003，DEV-030/033）**
  前置：标准 seed。步骤：①选 P_DSH 并依次看三视图；②选 P_LOCALPM；③选所有项目；④切换视图。断言：主任务数分别为2/2/4；各项目不会看到对方的任务；所有项目卡片能识别来源项目；切换不改数据。证据：查询结果和截图。

- [ ] **V-018 完成任务在矩阵显示（REQ-043，DEV-032）**
  前置：标准 seed。步骤：①矩阵默认查看 Q1；②开启「显示已完成」；③关闭开关；④确认看板完成列。断言：默认 Q1=0，开启后 Q1=1(T_D)，关闭后 Q1=0；T_D 的两个布尔位未变化，看板完成列一直显示 T_D。证据：断言和截图。

- [ ] **V-019 持久化与会话解耦（REQ-001/040/060，DEV-010/033）**
  前置：对 T_A 改状态、象限、描述、子任务完成状态。步骤：①刷新网页；②切换到 DSH 另一个聊天 Session；③关闭重开 DSH；④重新进入插件。断言：项目/任务/子任务数量、ID、状态、顺序、矩阵与描述完全一致；任务不随 Session 消失。证据：重启日志、前后数据库快照对比。

### 5.3 JSON 导入导出

- [ ] **V-020 DSH JSON 往返（REQ-050/051，DEV-040）**
  前置：标准 seed，另归档一个项目；导出完整 JSON；在**全新的测试库**中导入。断言：`format/schemaVersion` 存在，项目/父子/归档/状态/象限/排序字段的规范化数据集合与原库相等；无 DSH Session 或 Token。证据：导出文件 hash、规范化差异为 0 的测试输出。

- [ ] **V-021 重复导入幂等（REQ-051，DEV-040）**
  前置：空测试库。步骤：①导入 `dsh-valid.json`；②再次导入同文件；③检查预览与结果。断言：第二次新增项目0、主任务0、子任务0；原 ID、状态、内容不变；显示跳过数量，无重复任务。证据：前后计数、来源映射查询。

- [ ] **V-022 Super Productivity 已验证格式（REQ-052，DEV-041）**
  前置：A-004 的真实公开样本及已审查字段映射；空测试库。步骤：①导入前识别包装与版本；②预览项目/父子/完成/跳过条数；③确认；④核对项目、`parentId`、顺序、状态、矩阵默认值；⑤重复导入。断言：所有**支持范围内**实体成功映射且不重复；`isDone` 只映射 todo/done；默认 Q4；不支持字段显式列入报告。证据：样本来源/hash、映射快照、golden test。**样本不可得则本项 BLOCKED，不准 PASS。**

- [ ] **V-023 未知/旧版格式拒绝（REQ-052/053，DEV-041）**
  前置：`unsupported-version.json` 与已知旧格式样本。步骤：①尝试导入；②检查预览/错误。断言：未适配的版本拒绝并指明版本/原因；库内计数、hash 不变；不能把简单 `{tasks:[...]}` 误认成完整官方备份。证据：错误截图、快照一致性。

- [ ] **V-024 无效关系/中途失败回滚（REQ-051/053，DEV-040/041）**
  前置：有数据的测试库、损坏 JSON/重复 ID/孤儿子任务/失败注入。步骤：①逐份尝试导入；②在写入中人为抛错；③重新读取原库。断言：报错明确；所有失败操作前后的项目、任务总数及内容 hash 相同；无部分新增或关系断裂。证据：错误码、事务日志、前后 hash。

### 5.4 稳定性、体验与安全

- [ ] **V-025 离线使用（REQ-060，DEV-050）**
  前置：网络断开；新测试库。步骤：①打开插件；②创建/编辑任务、拖看板/矩阵、创建子任务；③本地导出/导入；④重启。断言：核心功能均可用，不出现必须登录/联网的阻塞。证据：网络状态与实际操作记录。

- [ ] **V-026 压力与性能（REQ-062，DEV-051）**
  前置：固定 20 项目/2,000 主任务/5,000 子任务 fixture；测试机器环境已记录。步骤：①冷启动页面；②切换 Scope 和三视图；③拖动/更新任务；④观察错误及内存。断言：无崩溃、无重复、数量准确、任务操作可完成；记录冷启动/P95 响应/峰值内存等实测值，性能不足必须优化后复测。证据：指标 CSV/日志与测试环境。

- [ ] **V-027 插件生命周期与数据安全（REQ-001/061，DEV-050）**
  前置：有数据的测试库。步骤：①停用插件；②确认 DSH 核心正常；③重新启用并重启；④检查原数据。断言：注册资源被正确释放，不产生重复菜单和事件；任务数据仍存在；不改其他插件数据。证据：日志、前后数据摘要。

- [ ] **V-028 键盘/非拖拽操作（REQ-024/042/043/062，DEV-050）**
  前置：标准 seed。步骤：①仅键盘打开任务详情和修改状态；②用卡片菜单改变看板列；③用菜单改变象限；④检查焦点和结果。断言：无拖拽亦能完成关键操作；焦点可见；状态/象限数据分别正确更新。证据：操作录屏或人工操作记录、字段断言。

- [ ] **V-029 写入失败、重复提交与并发（REQ-040/061，DEV-010/050）**
  前置：标准 seed。步骤：①模拟数据库不可写或保存异常；②重复快速提交一次创建；③模拟两个编辑来源相继更新相同任务。断言：失败有提示且 UI 回滚；重复提交不能生成两个相同请求实体；并发修改不可静默覆盖未经确认的数据。证据：日志、结果表与冲突处理说明。

- [ ] **V-030 安全与隐私（REQ-060/061，DEV-050）**
  前置：任务描述含脚本样例、导入文件含多余 token 字段。步骤：①查看标题/描述；②导入/导出；③检查浏览器网络与调试日志。断言：无脚本执行；无远端提交任务内容；导出不含 DSH Token/Session；日志不含完整敏感任务正文。证据：日志摘录、网络记录、安全断言。

## 7. Agent 编码与 QA 分工约定

### 主开发 Agent

1. 读取两份文档、现有项目贡献规范和官方 DSH 插件 Skill。
2. 执行 A-001 至 A-005，形成 Gate 0 结论；失败先修基座，不直接做大界面。
3. 逐个执行 DEV，保存源码、关联测试、实际运行命令和结果。
4. 每完成 DEV 就运行相关 V；失败修复并复测，不允许只打勾。
5. 所有需求变更必须同步更新两份文档、对应测试断言与 fixtures，不能只修改代码。
6. 阶段结束提交文件清单、失败记录、证据与下一阶段依赖。

### 独立 QA Agent

1. **不直接接受开发 Agent 的 PASS 结论**；自行阅读需求、代码与测试设施。
2. 用干净测试 Profile/fixture 重跑全部 P0 V；至少抽查项目→看板→矩阵→子任务→JSON 导出导入这一条 E2E 链路。
3. 对每项核对真实日志、字段断言和 UI 截图；检查是否把 `BLOCKED/NOT_RUN` 当 PASS。
4. 针对失败项给出可复现步骤、根因线索及缺陷编号；开发修复后重新验证。
5. 出具 `verification-report.md`，只在完整 P0 通过后签署通过。

## 8. 实施停机线与回滚

- 若插件装载需修改 DSH Core 私有文件或绕过安全边界：**停止并寻找正式扩展 API**。
- 若测试环境无法隔离真实用户任务：**停止破坏性测试**，先建立独立测试 Profile/DB。
- 若导入可能覆盖已存在任务或关系检查失败：**拒绝导入**，不做部分导入。
- 若跨视图数据出现不同步：先修统一 Repository/事件订阅，不用页面层复制数据掩盖问题。
- 若 SP 导出格式来源不可信：仅提供 DSH 原生导入导出，SP 兼容保留未完成，不做虚假的“支持所有版本”承诺。
- 若性能测试卡住主界面：记录指标、排查响应式渲染/查询索引，优化后重复基准测试。
