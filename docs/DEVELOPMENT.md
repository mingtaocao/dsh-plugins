# DSH 插件开发规范

适用于本仓库所有插件。目标是让 AI 和开发者按照相同流程开发、验证，而不是只写描述。

## 1. 先核实 DSH 机制（编码前必须）

- [ ] 确认 DSH 源码、官方 SDK 或插件开发文档，记录目标版本/commit。
- [ ] 查证插件入口、声明格式、安装/卸载方式、生命周期。
- [ ] 查证 UI 扩展点、数据持久化、权限、安全隔离和构建要求。
- [ ] 制作最小插件，验证安装 → 加载 → 显示 → 禁用 → 卸载。
- [ ] 在插件文档中记录以上证据（源码路径或官方文档）。

**不允许**凭经验虚构 DSH 的 API、manifest、目录格式或构建命令；未验证的部分标记为「待确认」。

## 2. 需求 → 设计 → 计划

每个插件开发前至少明确：

1. 目标、用户场景、范围及明确不做的功能。
2. 关键交互、状态、数据规则、失败和边界场景。
3. 技术设计：模块边界、数据模型、权限/安全、与宿主的接口。
4. 实施计划：按独立可验收的小任务拆分。
5. 验收用例：每项包含操作步骤、预期结果、异常路径。

需求变更后同步修订设计、计划和验收，不允许只改代码。

## 3. 开发约束

- 一个插件一个目录，代码、依赖、测试和文档独立。
- 优先使用 DSH 正式扩展点，不直接修改宿主源码。
- UI 遵循宿主现有主题、交互与布局；阅读优先、界面简洁。
- 文件访问、HTML 内容、外部资源及本地数据遵循最小权限原则。
- 出错须显示具体原因与可操作的恢复路径，不能静默空白。
- 不引入与需求无关的配置或抽象；不改动其他插件。
- 每次提交说明修改范围、对应需求和真实验证结果。
